## 1. Полный алгоритм банкира

Формула:

```text
Need[i] = Max[i] - Allocation[i]
```

Проверка безопасности использует `Work = Available`. Если для процесса выполняется `Need[i] <= Work`, считаем, что он может завершиться, и обязательно возвращаем его занятые ресурсы:

```text
Work = Work + Allocation[i]
```

### Проверка bank1

```bash
python3 banker.py bank1.txt --once
```

Результат:

```text
SAFE: P1 -> P3 -> P4 -> P2 -> P0
```

Это совпадает с эталонной безопасной последовательностью из условия.

### Проверка bank2

```bash
python3 banker.py bank2.txt --once
```

Результат:

```text
UNSAFE (only finishable prefix: <none>)
```

### Запросы из stdin

Запуск:

```bash
python3 banker.py bank1.txt
```

Формат запроса:

```text
request P1 1 0 2
```

Поддерживаются также команды:

```text
status
safety
quit
```

Для запроса `P1 (1, 0, 2)` результат:

```text
GRANTED P1 (1, 0, 2): request granted
Safe sequence: P1 -> P3 -> P4 -> P2 -> P0
```

Алгоритм сначала проверяет:

1. `Request <= Need`;
2. `Request <= Available`;
3. временно выдаёт ресурсы;
4. повторно выполняет safety check;
5. если состояние стало небезопасным — полностью откатывает изменения.

Пример запроса, который проходит первые две проверки, но создаёт небезопасное состояние:

```text
request P0 0 0 2
```

Результат:

```text
DENIED P0 (0, 0, 2): request would make the state UNSAFE; rolled back
```

После отказа `Available` снова равен `(3, 3, 2)`, то есть rollback действительно выполнен.

## 2. Детектор взаимоблокировок по графу ожидания

Журнал состоит из событий:

```text
acquire <process> <resource>
release <process> <resource>
wait <process> <resource>
```

Для единичных ресурсов строится **wait-for graph**: если `Pi` ждёт ресурс, которым владеет `Pj`, добавляется ребро:

```text
Pi -> Pj
```

Затем цикл ищется DFS с тремя состояниями вершины: `unvisited`, `active`, `finished`. Ребро в активную вершину означает цикл.

### Журнал с deadlock

```bash
python3 wait_graph_detector.py journal_deadlock.txt
```

Результат:

```text
Wait-for graph:
  P0 -> P1
  P1 -> P0
DEADLOCK: P0 -> P1 -> P0
Participants: P0, P1
```

Программа завершится с кодом `2`, потому что deadlock обнаружен.

### Журнал без deadlock

```bash
python3 wait_graph_detector.py journal_safe.txt
```

Результат:

```text
Wait-for graph:
  <empty>
NO DEADLOCK
```

## 3. TrackedLock — обнаружение цикла до зависания

`TrackedLock` оборачивает обычный `threading.Lock`. Для каждого lock хранится владелец, а для каждого ожидающего потока — lock, который он пытается получить.

Перед блокирующим `acquire()` строится текущий wait-for graph потоков. Если новое ожидание замыкает цикл, `TrackedLock` удаляет это ожидание и выбрасывает:

```text
DeadlockDetected
```

### Сначала настоящий deadlock

```bash
python3 deadlock.py
```

Пример вывода:

```text
worker_a: acquired A
worker_b: acquired B
worker_a: waiting for B
worker_b: waiting for A
```

После этого программа **намеренно не завершается**: каждый поток держит один lock и бесконечно ждёт второй.

В Linux удобно убедиться в зависании так:

```bash
timeout 3s python3 deadlock.py
```

`timeout` завершит зависшую программу через 3 секунды. Без `timeout` остановить её можно `Ctrl+C`/прерыванием процесса.

Здесь выполнены все четыре условия Coffman: mutual exclusion, hold and wait, no preemption и circular wait.

### Та же ситуация с TrackedLock

```bash
python3 tracked_deadlock_demo.py
```

Пример результата:

```text
worker_a: wait-for cycle detected: worker-a -> worker-b -> worker-a
Finished without hanging: TrackedLock rejected the cyclic acquire.
```

Один из потоков получает исключение, освобождает уже удерживаемый lock через context manager, после чего второй поток может завершиться. Реального зависания нет.

## 4. Обедающие философы

Запустить сразу все варианты:

```bash
python3 philosophers.py --mode all --duration 1
```

Или отдельно:

```bash
python3 philosophers.py --mode deadlock --duration 1
python3 philosophers.py --mode ordered --duration 2
python3 philosophers.py --mode waiter --duration 2
```

### Вариант 1 — намеренный deadlock

Все 5 философов сначала захватывают левую вилку. `Barrier` гарантирует, что каждый уже держит свою левую вилку, прежде чем кто-либо попробует взять правую. В результате возникает цикл из пяти потоков.

Фактический тест:

| Философ | Сколько раз поел |
|---|---:|
| P0 | 0 |
| P1 | 0 |
| P2 | 0 |
| P3 | 0 |
| P4 | 0 |

Итого: `0`; все `5/5` потоков заблокированы.

### Исправление 1 — глобальная нумерация вилок

Каждый философ всегда берёт вилку с меньшим номером первой, затем с большим. Циклическое ожидание становится невозможным.

Пример теста за 1 секунду:

| Философ | Сколько раз поел |
|---|---:|
| P0 | 400 |
| P1 | 413 |
| P2 | 415 |
| P3 | 430 |
| P4 | 409 |
| **Всего** | **2067** |

### Исправление 2 — официант / ограничение N−1

Перед захватом вилок философ должен получить разрешение семафора:

```python
threading.Semaphore(N - 1)
```

При пяти философах одновременно к вилкам допускаются максимум четыре. Поэтому невозможно состояние, где все пять удерживают по одной вилке и ждут следующую.

Пример теста за 1 секунду:

| Философ | Сколько раз поел |
|---|---:|
| P0 | 402 |
| P1 | 411 |
| P2 | 409 |
| P3 | 408 |
| P4 | 398 |
| **Всего** | **2028** |

Точные числа зависят от ОС, планировщика и нагрузки компьютера; важно различие: deadlock даёт нулевой прогресс, а оба исправления продолжают работу.

# Контрольные вопросы

## 1. Почему упорядочивание захвата ресурсов исключает deadlock?

Deadlock требует **циклического ожидания**. Например:

```text
P0 ждёт ресурс P1
P1 ждёт ресурс P2
P2 ждёт ресурс P0
```

Если всем ресурсам назначить глобальный порядок и разрешить брать их только по возрастанию номера, цикл невозможен. Для образования цикла последний участник должен был бы ждать ресурс с меньшим номером, чем уже удерживаемый, а правило это запрещает.

То есть упорядочивание нарушает одно из четырёх необходимых условий Coffman — **circular wait**.

## 2. Почему алгоритм банкира редко применяется в универсальных ОС?

Алгоритму банкира заранее нужны максимальные потребности каждого процесса (`Max`). В универсальной ОС обычно невозможно заранее знать, сколько памяти, файлов, lock-ов, устройств или других ресурсов программа потребует за всё время работы.

Кроме того:

- набор процессов постоянно меняется;
- количество доступных ресурсов тоже может меняться;
- safety check создаёт дополнительные вычислительные расходы;
- слишком осторожное резервирование снижает использование ресурсов;
- современные ОС чаще применяют более специализированные механизмы: порядок lock-ов, timeouts, detection/recovery, ограничения ресурсов и правила конкретных подсистем.

Поэтому алгоритм банкира важен как модель **избежания deadlock**, но неудобен как общий механизм управления ресурсами универсальной ОС.

## Краткий вывод

В работе реализованы три разных подхода к проблеме deadlock:

1. **Избежание** — алгоритм банкира не разрешает переход в небезопасное состояние.
2. **Обнаружение** — DFS на wait-for graph находит уже существующий цикл ожидания.
3. **Предотвращение** — `TrackedLock`, глобальный порядок вилок и семафор `N-1` не дают системе попасть в deadlock.
