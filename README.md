## Выполнение задания

### 1. Полный алгоритм банкира

Для каждого процесса вычисляется:

```text
Need[i] = Max[i] - Allocation[i]
```

Проверка безопасности начинается с:

```text
Work = Available
```

Если для процесса выполняется `Need[i] <= Work`, считается, что он может завершиться, после чего его занятые ресурсы возвращаются:

```text
Work = Work + Allocation[i]
```

Для `bank1.txt` получена эталонная последовательность:

```text
SAFE: P1 -> P3 -> P4 -> P2 -> P0
```

Для `bank2.txt`:

```text
UNSAFE
```

### 2. Обработка запросов `request(pid, vector)`

Перед выдачей ресурса проверяется:

1. `Request <= Need`;
2. `Request <= Available`;
3. ресурсы временно выделяются;
4. выполняется новый safety check;
5. если состояние становится небезопасным — изменения полностью откатываются.

Запрос:

```text
request P1 1 0 2
```

разрешается.

Пример запроса, который после временной выдачи приводит к unsafe-state, отклоняется, а `Available` и `Allocation` возвращаются к исходным значениям.

### 3. Wait-for graph

Для единичных ресурсов строится граф ожидания. Если процесс `Pi` ждёт ресурс, которым владеет `Pj`, добавляется ребро:

```text
Pi -> Pj
```

Цикл ищется алгоритмом DFS.

Для `journal_deadlock.txt` получается:

```text
P0 -> P1
P1 -> P0
DEADLOCK: P0 -> P1 -> P0
```

Участники цикла явно выводятся программой.

### 4. TrackedLock

`TrackedLock` оборачивает `threading.Lock` и хранит информацию:

- какой поток владеет lock;
- какой поток какой lock ожидает.

Перед блокирующим захватом строится текущий wait-for graph. Если новая зависимость замыкает цикл, вместо зависания выбрасывается исключение `DeadlockDetected`.

Таким образом, классическая ситуация из `deadlock.py` превращается из бесконечного ожидания в контролируемую ошибку.

### 5. Настоящий deadlock

`deadlock.py` создаёт два потока:

- первый захватывает `A` и ждёт `B`;
- второй захватывает `B` и ждёт `A`.

Выполняются все четыре условия Coffman:

1. mutual exclusion;
2. hold and wait;
3. no preemption;
4. circular wait.

### 6. Обедающие философы

Реализованы три режима.

**Наивный вариант:** все пять философов берут левую вилку и затем ждут правую. Возникает цикл ожидания, прогресс останавливается.

Контрольная статистика:

```text
P0: 0
P1: 0
P2: 0
P3: 0
P4: 0
```

**Исправление 1 — глобальная нумерация вилок.** Каждый философ всегда берёт сначала вилку с меньшим номером, затем с большим. Circular wait становится невозможен.

**Исправление 2 — семафор N−1.** Одновременно к вилкам допускаются максимум четыре философа из пяти. Поэтому состояние, в котором все удерживают по одной вилке, не возникает.

Оба исправления показывают ненулевое количество приёмов пищи у всех философов.

## Ответы на контрольные вопросы

### Почему упорядочивание ресурсов исключает deadlock?

Deadlock требует циклического ожидания. Если все потоки обязаны захватывать ресурсы только в одном глобальном порядке, последний участник потенциального цикла не сможет ждать ресурс с меньшим номером, чем уже удерживаемый. Следовательно, условие `circular wait` нарушается.

### Почему алгоритм банкира редко используется в универсальных ОС?

Алгоритму заранее нужны максимальные потребности процессов в ресурсах. В обычной ОС заранее неизвестно, сколько памяти, файлов, lock-ов или устройств потребуется произвольной программе. Кроме того, постоянные safety check создают накладные расходы и могут слишком консервативно ограничивать использование ресурсов.

## Вывод

В работе рассмотрены три подхода к проблеме взаимоблокировок: **избежание** через алгоритм банкира, **обнаружение** через цикл в wait-for graph и **предотвращение** через правила захвата ресурсов.
